# システムコンセプト

日常の活動ログを収集・構造化し、AIによる要約記事を生成してブログへ下書きとして連携するパイプラインの概念定義である。

## 基本思想

### 自動収集とダイジェスト化

日々の開発作業や情報整理で利用するツールから活動記録を自動収集し、定期的なダイジェスト記事として再構成する。執筆にかかる初動コストを排除し、活動履歴を公開可能な記録として蓄積する。

### 人間が執筆する記事との明確な分離

AIによって自動生成された記録であることを明記し、通常の技術考察や論説記事とはカテゴリや著者属性を分離して管理する。

### 下書き連携と人間による検査

生成された記事は即座に公開せず、ブログプラットフォームへ下書きとして保存する。公開前に人間が目を通し、必要に応じて修正や追記を行う検査フローを前提とする。

### 差し替え可能なモジュラー設計

データソース、要約エンジン、実行基盤、投稿先の各コンポーネントを疎結合に保つ。特定の外部サービスに依存せず、インターフェースを介して差し替え可能な構造とする。

## 概念アーキテクチャ

システムは以下の論理レイヤーで構成する。

`mermaid
flowchart LR
    subgraph Sources [活動データソース]
        S1[ソース A]
        S2[ソース B]
        S3[ソース C]
    end

    subgraph Core [集約・生成コア]
        Collector[データ収集・正規化]
        Generator[ダイジェスト生成エンジン]
        Validator[構造・形式検証]
    end

    subgraph Destination [公開先プラットフォーム]
        Publisher[パブリッシュアダプタ]
        CMS[コンテンツ管理システム / ブログ]
    end

    Sources --> Collector
    Collector -->|正規化データ| Generator
    Generator -->|生成コンテンツ| Validator
    Validator -->|検証済みドラフト| Publisher
    Publisher -->|下書き登録| CMS
`

### レイヤー責務

- 活動データソース: 各種サービスから対象期間内のイベント、タスク、履歴データを取得する。
- データ収集・正規化: ソース固有のレスポンスから不要なノイズを除去し、共通スキーマに変換する。
- ダイジェスト生成エンジン: プロンプトと正規化データを入力とし、指定されたスキーマに従った記事（タイトル、本文、抜粋、タグ等）を生成する。
- 構造・形式検証: 生成物のJSONスキーマ適合性、必須項目の欠損、マークダウンの構文妥当性を機械的に検証する。
- パブリッシュアダプタ: 検証済みデータを対象プラットフォームのAPI仕様に合わせて送信し、下書きとして登録する。

## データフロー

1. 定期トリガーによるパイプライン起動。
2. 対象期間（例: 直近7日間）の活動データを各データソースから並行取得。
3. 取得データのフィルタリングと要約用共通フォーマットへの集約。
4. 生成エンジンへのプロンプト投入と構造化レスポンスの受信。
5. 生成物に対するバリデーション（スキーマ・マークダウン構文）。
6. 検証済みコンテンツのブログプラットフォームへの下書き登録。

## 実装構成の選択肢

各論理レイヤーの実装候補を以下に示す。要件や運用環境に応じて個別に選定および差し替えが可能である。

### データソースの候補

- 開発履歴: GitHub（コミットログ、プルリクエスト、Issue）
- タスク・ノート: Notion（完了タスク、日報・作業メモデータベース）
- 記事・ブックマーク: Pocket、Raindrop、RSSフィード、ブラウザ履歴
- 位置・行動ログ: Google Mapsタイムライン、カレンダー予定

### 生成エンジンの候補

- クラウドLLM API: Google Gemini API、OpenAI API、Anthropic API
- ローカルLLM: Ollama、vLLMなどのセルフホスト推論基盤
- 自律型エージェント: Coding AgentによるCLI/ツール経由のバッチ処理

### 形式検証の方式

- APIレベルの制約: Structured Outputs（JSON Schema拘束）
- アプリケーション検証: Pydanticなどの型定義ライブラリによる値検証
- 構文検証: マークダウンパーサーによるパース可否判定

### パブリッシュ先アダプタの候補

- WordPress: REST API（Application Passwords認証）による下書き投稿
- ヘッドライン / ヘッドレスCMS: MicroCMS、Strapi、Contentful
- 静的サイトリポジトリ: GitHubリポジトリへのプルリクエスト作成またはコミット

### 実行環境の候補

- CI/CDスケジューラ: GitHub Actionsの定期実行ワークフロー
- クラウドコンテナ / サーバレス: Cloud Run Jobs、AWS Lambda + EventBridge
- ローカル環境: OSタスクスケジューラ、cron
